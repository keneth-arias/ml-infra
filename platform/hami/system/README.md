# HAMi system bundle

The bundle uses the official HAMi 2.11.0 chart and the Kubernetes 1.36.3 kube-scheduler image. Release images are pinned by OCI index digest. Run `uv run render.py --check` with Helm 3 installed to compare the checked-in manifests against the pinned chart. Pass `--chart /path/to/hami-2.11.0.tgz` to use an existing copy of the archive. Run `kubectl kustomize .` to render the Flux resource set. [HAMi release](https://github.com/Project-HAMi/HAMi/releases/tag/v2.11.0)

The Flux root contains the scheduler, the device plugin and their namespaced resources. The operator owns `runtime-access.yaml`, the `hami-system/hami-scheduler-tls` Secret and the CA-populated copy of `operator/webhook.yaml`. Set the server certificate SAN to `hami-scheduler.hami-system.svc` and stage the Secret with `tls.crt` and `tls.key` before reconciling the scheduler. Once it is Ready, inject the base64-encoded PEM issuing CA into `webhooks[0].clientConfig.caBundle` before applying the webhook. The webhook fails closed on Pod creation and updates in `hami-workloads` only. The scheduler requires workloads to select `hami-scheduler` explicitly. [Upstream TLS settings](https://github.com/Project-HAMi/HAMi/blob/v2.11.0/charts/hami/values.yaml)

The scheduler runs on `airaware.training/pool=training-cpu`. The device plugin selects nodes that carry both `airaware.training/gpu-mode=hami` and `gpu=on`. Keep the exclusive HAMi label absent for the CPU-only stage. A GPU pilot needs a dedicated, tainted node pool, an existing `nvidia` RuntimeClass that works with the NVIDIA runtime and driver on that pool, and confirmed exclusion from native GPU consumers. The device plugin uses NVIDIA's environment variable injection and grants the trusted plugin host access to the kubelet device-plugin socket and other host paths. The scheduler and plugin use ClusterIP Services. The extender's scheduling endpoints and scheduler metrics listen on loopback. Runtime identities retain the upstream Kubernetes scheduler and HAMi permissions, including cluster-wide node and Pod access. [Chart reference](https://github.com/Project-HAMi/HAMi/blob/v2.11.0/charts/hami/README.md)

HAMi advertises up to four `hami.io/gpu` slots per eligible physical GPU. A slot is a scheduling count. Set `hami.io/gpumem` in MiB or `hami.io/gpumem-percentage` as an integer percentage of each selected card. Set `hami.io/gpucores` as an integer percentage to request compute sharing. A count with no memory or core limits requests the full GPU. The pilot requires an explicit count and its memory and core scaling factors are both 1. The upstream chart defaults to ten slots and the same `nvidia.com/gpu` name as the native plugin. Distinct resource names avoid registration collisions. They still allow two independent device plugins to allocate the same physical GPU, so keep native `nvidia.com/gpu` workloads on their own node pool. [GPU allocation settings](https://github.com/Project-HAMi/HAMi/blob/v2.11.0/charts/hami/values.yaml) [HAMi resource names](https://project-hami.io/docs/faq)

For rollback, stop pilot submissions and drain pilot GPU workloads before removing the webhook or device plugin. Remove the webhook before stopping the scheduler so fail-closed admission does not strand the pilot namespace. Verify that the HAMi resource and registration disappear from the dedicated pool before releasing that pool. Retire the scheduler TLS Secret and runtime RBAC after the owning Pods are gone.
